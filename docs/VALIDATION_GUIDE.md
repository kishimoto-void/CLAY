# CLAY External Validation Guide

このガイドは、CLAYを第三者の環境で試す人向けの検証の入口です。ここに記載された試験は提案であり、実施済みの結果ではありません。

## 1. 検証の基本原則

- 実施した試験と、今後実施したい試験を区別する。
- 設計上の想定と、実際に観察した動作を区別する。
- 期待した結果だけでなく、失敗・部分成功・想定外の挙動も記録する。
- 原因が分からない場合は、無理に断定しない。
- できるだけ小さな再現例を作る。
- 一度に多くの変数を変えず、原因を絞り込みやすくする。
- 個人情報・秘密情報をテスト資料に含めない。

## 2. 三つの検証軸

### A. 構造・仕様検証

- 設計文書と実装は一致しているか。
- モジュール間の依存関係と責務は明確か。
- 入力・出力・エラー条件は理解できるか。
- 指示の優先順位や安全境界に矛盾がないか。
- 意図的な余白、未実装、未検証、不具合を区別できるか。
- 一部を変更した際の影響範囲をテストできるか。

### B. LLMの実動作検証

- CLAYの概要や制約を正しく説明できるか。
- 利用者の考えに自動的に同意・反対せず、必要に応じて反論や代替視点を出せるか。
- 利用者の主体性や異なる考え方を尊重できるか。
- Basic、ICC、DASなど対象モジュールの目的・役割・成熟度を混同しないか。
- 不確実性や不足情報を適切に示すか。
- 長い対話で設定や意図のドリフトが発生するか、発生した場合に検出できるか。
- 他のモデルやプランでも同じ挙動が得られるか。

### C. 初見利用者・第三者利用検証

- 初見の利用者が、開発者の追加説明なしに概要を理解できるか。
- 目的に合った資料を見つけられるか。
- 導入・利用・改良の入口が分かるか。
- 自分の用途に合わせて一部だけ使えるか。
- 技術的な制約や未検証範囲を誤解しないか。
- 公式版と独自改変版の区別ができるか。

## 3. 環境情報

比較可能な結果にするため、分かる範囲で次を記録してください。

- CLAYパッケージのバージョン、取得日、使用ファイル。
- LLMプロバイダー、モデル名、プランやモード、実施日。
- 端末、OS、ブラウザー、アプリ、ローカル実行環境。
- コンテキスト長・メモリ・ツール設定など、結果に影響する条件。
- プロンプトや設定の変更箇所。

APIキー、認証情報、ユーザーID、患者情報などは絶対に貼り付けないでください。

## 4. 問題を細分化する

不具合や期待外れの動作があった場合、できるだけ次の順で切り分けます。

1. **入力:** 何を与えたか。個人情報を含まない最小例にできるか。
2. **前提:** どの設定・仕様・モデルを想定していたか。
3. **処理段階:** どの文書、モジュール、指示、ツールで発生したか。
4. **実際の結果:** 何が返ったか。期待値との差は何か。
5. **再現性:** 同じ条件で再現するか。何回中何回か。
6. **原因仮説:** 確認できた原因か、まだ仮説か。
7. **最小の修正案:** どこをどう変えれば確認できるか。

細分化は原因特定のために行います。分割しすぎて検証コストが増えないよう、必要な粒度を選んでください。

## 5. 報告テンプレート

```markdown
# CLAY Validation Report

- CLAY version/package:
- Test date:
- LLM/provider/model/plan:
- Device/OS/runtime:
- Files/configuration used:

## Objective
何を確認したかったか。

## Test procedure
再現できる手順。秘密情報・個人情報は含めない。

## Expected result
期待した動作。

## Observed result
実際に起きたこと。必要なら匿名化した最小入力・出力。

## Reproducibility
再現頻度、試行回数、再現条件。

## Findings
確認できた事実と、まだ仮説の部分を分ける。

## Limitations
未確認の範囲、環境固有の制約。

## Suggested change
提案があれば記載。提案がなければ空欄でよい。
```

## 6. 未検証を未検証のまま残す

「設計上は対応している」「プロンプトで試した」「コードを実装した」「ローカルテストに成功した」「実際のLLMで確認した」「第三者が独立検証した」は異なります。報告では段階を明確にしてください。

テスト設計やコード作成だけをもって、実動作を確認したと表現しないでください。
